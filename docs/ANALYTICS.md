# Local balance analytics

Implemented 30 October 2026. Collection is local only; no upload endpoint, automatic submission, account identifier, player name, device identifier, or persistent player identifier is used. Normal multiplayer gameplay still uses its existing networking. This recorder makes no analytics network calls and does not call s&box Stats.

## Storage and lifecycle

`FileSystem.Data` stores recordings beneath `analytics/v1`. The engine controls the physical game-data root; the full file path is printed in the game console as `City Sim local analytics: ...` when recording starts. This deliberately uses persistent game data rather than the cache or project assets.

Each recording is a UTF-8 `.jsonl` file (one JSON event per line). Events are serialized, appended, and the file handle closed immediately, including purchases before a market resolves. A crash may leave an incomplete final line: importers should accept earlier complete lines and report the trailing fragment. This is not a transaction log or guaranteed recovery from power failure.

Solo and sandbox games record on the local machine. Multiplayer records all seats on the authoritative host only. Clients and spectators do not create duplicate copies. Host migration starts a new recording segment on the new host, using the same match ID and a new recording ID; earlier files stay on the former host. Interrupted recordings retain their partial data. `recording_stopped` means authority detached, which may be a menu exit, shutdown, rematch, or migration; it is not automatically a player abandonment. A crash has no terminal event.

Files are capped at 2 MiB each and 64 files per game-data folder (at most approximately 128 MiB generated by this recorder). Reaching either limit stops recording and logs a warning. Existing recordings are never automatically deleted. Moving or deleting old files frees space for future recordings. Write failures disable the affected recorder and log once; gameplay continues. There is no settings UI for storage yet.

## Schema v1

Each event has `SchemaVersion`, `BalanceVersion`, `RecordingId`, `MatchId`, `Sequence`, UTC `TimestampUtc`, `Round`, `Phase`, `Event`, and `Data`. Sequence starts at one per recording. Seats are zero-based numbers assigned from the match's player order; neutral board cells use a null seat. Random match/recording IDs correlate gameplay, not accounts. Bump `BalanceAnalytics.BalanceVersion` whenever scoring or card balance changes; bump schema version for incompatible format changes. The starting event also captures the complete card catalogue and match settings so tuning remains interpretable.

| Event | Contents / purpose |
| --- | --- |
| `recording_started` | Mode, aggregate bot difficulties, bot seats with individual difficulty/style, seed, dimensions, settings, catalogue, initial hands/resources/board, and whether joining an existing round |
| `market_offered` | Per-seat market ID, lot IDs, card IDs, prices, budget, eligibility/readiness and whether each lot is allowed; emitted when the market opens, or when recording resumes during a market |
| `card_received` | Successful card addition to hand, including defaults, effects and purchases |
| `card_purchased` | Committed purchase, seat, card, market/lot, price and remaining coins |
| `market_resolved` | Eligible participants, paid amounts and whether they finished without buying |
| `card_played` | Placement with coordinates and attributed VP/coin awards, or consumed event card with effect coins and claim coordinates |
| `card_discarded` | Deliberate successful hand discard |
| `building_replaced` | Renovation's removed and replacement buildings |
| `building_grown` | Growth transformation and its park awards |
| `phase_started` | All seats' hands, coins and VP at the phase boundary |
| `payout_resolved` | Income/VP entries, reasons and source/partner buildings, plus resource/hand snapshots |
| `match_completed` | Final score breakdown, winning seats, remaining hands and board |
| `recording_stopped` | Partial recording's final hand/resource snapshot |

Rejected requests and previews are not recorded as purchases or plays. Purchase is a subset of receipt: do not add those counts together. Renovation consumes an event card and a replacement building, so legitimately emits two plays plus a replacement event. Growth is not a hand-card play. A phase snapshot is a point-in-time view: payout/growth and final scoring have their own subsequent events. The completion event can precede the EndGame phase notification; its event name is the completion signal.

## First balance reports

Balance version `2026-10-30.5` adds weighted AI choices at all three difficulties while retaining the `.4` placement rules. Use this version to separate recordings from the previous mostly deterministic AI. Difficulty probabilities and verification are documented in [weighted AI choices](AI_WEIGHTED_CHOICES.md).

1. **Market preference:** purchases divided by eligible, allowed offers for each card and price. Restrict denominators to players who could act; show unaffordable/ownership-blocked offers separately. A resumed segment's offer snapshot is not a new market exposure. Players may buy the same lot independently.
2. **Card usefulness:** plays, deliberate discards and cards still held at completion. Track receipt-to-play lag by round; identical copies have no individual instance ID, so use a documented FIFO attribution approximation where necessary.
3. **Economy and score:** per-round coin/VP curves, card-sourced payout and placement awards, end-game card awards, acquisition spending and unused coins. Some shared effects and event bonuses are attributed by reason rather than a unique card instance. Do not infer a card's complete causal contribution from direct awards alone.
4. **Outcomes:** card ownership/purchases versus final score and fractional tied-win share. Split by balance version, player count, mode, bots versus humans, difficulty, round acquired and settings. Report sample sizes. Winning-player card correlations are observational, not proof of an overpowered card.
5. **Quality:** completed versus partial recordings, missing sequence numbers, truncated lines, duplicate uploads and migration coverage. Do not mix incomplete recordings into win-rate denominators. If migration segments overlap, reconcile by match, seat, market ID/lot and board placement order; conflicting histories should be flagged. Event sequence alone only deduplicates within a recording.

## Future opt-in upload (not implemented)

- Add a player-facing explanation, collection controls, storage usage, preview/export/delete, and explicit selection of recordings to upload. Account for hosts' recordings containing match-local activity from other participants.
- Upload closed recordings only, with limits, transport security, retry/backoff, server schema validation and idempotency on recording ID + sequence. Treat client-produced logs as untrusted; they are suitable for balancing, not competitive enforcement.
- Keep local files unless the player chooses deletion. Record upload receipts separately. Support partial recordings and multiple hosts uploading segments of one match without counting the match twice.
- Build an offline importer/report around the metrics above before adding a backend. Test interrupted writes, missing segments, full storage, offline uploads, duplicate submissions and consent withdrawal.

## s&box built-in services

s&box provides [Stats](https://sbox.game/dev/doc/services/stats) for per-player and global aggregates, with increment/set APIs and optional attached data. Submissions are batched and sent to its backend. Stats also underpin leaderboards. These could later complement an explicitly enabled aggregate telemetry feature, but do not satisfy local storage with a later player-selected upload. Consequently this implementation uses `FileSystem.Data` and does not enable those services.

## Verification

Run from the project folder:

```powershell
dotnet run --project tests/CitySim.Rules.Tests.csproj
```

Analytics checks cover eligible offer recording, invalid/replayed purchases, immediate purchase notification, placement/event plays, discards, identity stripping, sequencing, detachment, completed outcomes, segment identity, and storage-error isolation. The existing rules suite also runs. A .NET game-project build checks engine API signatures; live engine allowlist/file persistence should additionally be checked in a running s&box session by starting a match, buying/playing a card, returning to menu and reading the printed JSONL path.
